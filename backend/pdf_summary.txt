 ТЕХНИЧЕСКОЕ
 ЗАДАНИЕ
 TeamMind — интеллектуальный помощник
 для формирования рабочих команд
Тип: кроссплатформенное desktop-приложение для управления проектными командами.
Цель: анализировать загрузку, отпуска, навыки и рабочие предпочтения сотрудников, чтобы
предлагать сбалансированные команды.
Компонент
Технологии и назначение
Frontend
React + TypeScript + Vite — интерфейс и клиентская логика
Desktop
Electron — настольная оболочка и сборка приложения
Backend
Python + Django REST Framework — бизнес-логика и REST API
GraphQL
Graphene-Django или Strawberry — гибкие запросы и мутации данных
База данных
PostgreSQL — постоянное хранение данных
Дополнительно
JWT, Recharts, Docker Compose, pytest, Git
Документ для командной разработки в рамках учебного проекта колледжа.

1. Общая информация
Заказчик — организация, сотрудники которой объединяются в группы для выполнения проектов.
Исполнитель разрабатывает desktop-приложение для управления сотрудниками, проектами,
отпусками и автоматического формирования рабочих команд.
Основной результат: руководитель задаёт требования проекта, система анализирует доступность
сотрудников и предлагает несколько подходящих составов с оценкой и объяснением решения.
2. Роли пользователей
Администратор
• Создаёт учётные записи, назначает роли и управляет отделами и справочниками.
• Настраивает права доступа и просматривает журнал важных действий.
Руководитель проекта
• Создаёт проекты и задачи, задаёт сроки, необходимые навыки и число участников.
• Просматривает загрузку и отпуска, запускает алгоритм формирования команд.
• Сравнивает варианты, редактирует состав и утверждает команду.
Сотрудник
• Обновляет доступные поля профиля, навыки и рабочие предпочтения.
• Указывает хронотип и предпочтительные часы встреч.
• Подаёт сведения об отпуске и просматривает свои назначения.
3. Функциональные требования
3.1. Авторизация и доступ
• Вход по логину и паролю, выход из системы и безопасное хранение паролей.
• Разграничение функций по ролям с обязательной проверкой разрешений на backend.
• Защита REST и GraphQL API от неавторизованных запросов.
• Создание учётных записей администратором; восстановление пароля — дополнительная
функция.
3.2. Управление сотрудниками
Карточка сотрудника содержит ФИО, должность, отдел, навыки и уровни навыков, доступные
рабочие часы в неделю, текущую загрузку, хронотип, предпочтительный интервал работы и статус
доступности. Реализовать поиск, фильтрацию, сортировку, создание, редактирование и
архивирование.
3.3. Календарь отпусков
• Просмотр отпусков по сотрудникам и отделам.
• Создание и редактирование периодов; статусы: ожидает подтверждения, одобрен, отклонён.
• Предупреждение об отсутствии необходимых специалистов в период проекта.
• Одобренный отпуск, пересекающийся с проектом, исключает сотрудника из доступных
кандидатов
на этот период.

4. Анализ загрузки и рабочих предпочтений
4.1. Загрузка сотрудников
Загрузка рассчитывается как занятые рабочие часы / доступные рабочие часы × 100%. Система
показывает процент занятости, выявляет перегрузку, ищет свободных специалистов, сравнивает
отделы и прогнозирует нагрузку после назначения на проект.
4.2. Хронотипы
Сотрудник может выбрать «жаворонок», «сова» или «промежуточный тип» и указать
предпочтительные часы встреч. Алгоритм учитывает пересечение доступных интервалов.
Хронотип
используется как рабочее предпочтение, а не как показатель профессиональной пригодности.
4.3. Совместимость
• Совпадение предпочтительных часов работы.
• Предпочтения по коммуникации и командной/самостоятельной работе.
• Взаимодополняющие навыки и добровольно указанные предпочтения взаимодействия.
• Выявление конфликтующих расписаний.
Система не ставит психологические диагнозы и не выдаёт субъективную совместимость за научно
доказанный факт. Результат является рекомендацией, которую руководитель может проверить и
изменить.
5. Алгоритм формирования команд
• Исключить сотрудников, недоступных в период проекта.
• Проверить обязательные навыки и минимальные уровни компетенций.
• Оценить свободную загрузку кандидатов.
• Учесть совместимость расписаний и рабочие предпочтения.
• Сформировать несколько вариантов, если это возможно.
• Рассчитать общий балл и объяснить причины выбора.
• Разрешить ручное изменение состава и утверждение руководителем.

Показывает количество сотрудников и активных проектов, сотрудников в отпуске, среднюю

отделов, распределение по хронотипам и последние запуски алгоритма.

7.1. Использование GraphQL
• Создать GraphQL endpoint, например /graphql/.
• Реализовать Query для сотрудников, проектов, отпусков, загрузки и вариантов команд.
• Реализовать Mutation для создания/редактирования сотрудников, проектов, отпусков и
утверждения команды.
• Проверять аутентификацию и права доступа для каждого запроса и поля, где это необходимо.
• Ограничить глубину и сложность запросов; использовать пагинацию и защиту от чрезмерной
выборки.
• Не дублировать без причины все REST endpoints: REST оставить для стандартных
CRUD/интеграционных сценариев, GraphQL — для гибких связанных выборок и сложных экранов.
Примеры операций: запрос карточки проекта вместе с участниками и требуемыми навыками;
получение загрузки сотрудников отдела; мутация запуска генерации команды.
• Генерация команды, построение больших отчётов и импорт таблиц выполняются асинхронно,
чтобы не блокировать интерфейс и HTTP-запрос.
• API возвращает идентификатор задачи и статус: queued, running, succeeded или failed.
• Frontend периодически запрашивает статус через API либо получает обновления через
WebSocket/SSE как дополнительную функцию.
• Обрабатывать повторные попытки, тайм-ауты и ошибки; задачи по возможности делать
идемпотентными.

13. Критерии приёмки
• Пользователь может войти, а система различает роли.
• Администратор управляет сотрудниками, отделами и навыками.
• Руководитель создаёт проекты и задачи.
• Отпуска и доступность учитываются при подборе кандидатов.
• Загрузка рассчитывается автоматически.
• Алгоритм учитывает навыки, нагрузку, расписания и обязательные ограничения.
• Для вариантов отображаются баллы, объяснения и предупреждения.
• Руководитель может изменить состав и утвердить команду.
• Данные сохраняются в PostgreSQL, аналитика отображает реальные данные.
• REST API и GraphQL работают с проверкой прав доступа.
• React-приложение запускается через Electron.
• Есть документация, автоматические тесты и инструкция запуска.
14. Что передать заказчику
• Исходный код React + TypeScript, Electron и Django.
• Схему базы данных и миграции.
• Документацию REST API и GraphQL-схемы.
• Инструкцию установки и запуска.
• Демонстрационные данные и автоматические тесты.
• Презентацию и демонстрацию полного сценария.

• Сравнение вариантов команды и What-if-анализ.
• Поиск дефицита компетенций по активным проектам.

• Уведомления о перегрузке и конфликтах расписаний.

• Оптимизация нескольких проектов одновременно.
